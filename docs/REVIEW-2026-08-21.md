# betterSleep — Final Adversarial Review (2026-08-21)

**Scope.** Report-only review of the completed BS-0…BS-6 build on `main` at `c172aa1`.
No file in the repository was changed. Method: six independent adversarial review
passes (quiz/archetypes, email-capture/CRM/nurture, landing/theme/i18n, content
pipeline/blog, shop/money/night-map, cross-cutting platform/ops), each verifying its
claims against the actual code — several against the live dev database — plus a full
run of the root quality gate.

**Gate evidence.** `pnpm lint && pnpm check && pnpm test:unit` passes from the repo
root (96 test files, 834 passed, 4 skipped, exit 0). The run emits a stream of Svelte
`state_referenced_locally` warnings from `packages/formcomp/dist` (see L-1).

**Headline.** The product-level work is genuinely strong — integer-bani discipline is
airtight, the webhook/idempotency layers are exemplary, content bundles diff clean
against their sources byte-for-byte, and the no-JS/reduced-motion landing story is
correct. The dangerous findings cluster on two seams:

1. **The mock-by-default pattern becomes a silent production hazard.** Stripe
   checkout, Stripe sync, the courier, and the chat provider all fall back to mocks
   when env is missing — and `launch:check` catches none of it. A "live" deploy today
   sends paying customers to a dead stripe.com URL. (C-1, H-7, H-8, H-9)
2. **Public-endpoint abuse economics.** The quiz submit endpoint is unthrottled, the
   shared global email budget can be drained by one IP, and double opt-in can be
   bypassed for previously-confirmed addresses. (H-2, H-3, H-4)

Severity legend: **C** critical · **H** high · **M** medium · **L** low.
Each item: what / why it matters / concrete fix. Findings marked PLAUSIBLE were
mechanically verified in code but depend on a deployment or legal fact to confirm.

## CRITICAL

### C-1. Keyless checkout redirects real customers to a dead `checkout.stripe.com` URL
**Where:** `apps/web/src/lib/modules/shop/server.ts:125-132`,
`modules/shop/mock-gateway.ts:24,69-88`, `routes/(public)/cos/+page.server.ts:110-128`.
**What.** With `STRIPE_SECRET_KEY` unset (the current, by-design state),
`getStripeGateway()` silently returns the mock, whose `createCheckoutSession` returns
`https://checkout.stripe.com/c/pay/cs_test_mock_1` — the **real** stripe.com origin —
and the cart action executes `redirect(303, url)`. Traced end-to-end; there is no
guard anywhere between "add real product" and the 303. `launch:check` only flags a
*test* key in a live env (`launch-check.ts:110-114`); a *missing* key passes clean,
and `env-matrix.ts` does not list `STRIPE_SECRET_KEY` at all.
**Why it matters.** On a live deploy today a customer fills the whole checkout form
and lands on Stripe's generic "Something went wrong" page — no error on our side, no
order, no telemetry, and it looks like Stripe's fault.
**Fix.** (a) In `launchCheckProblems`, when `EMAIL_DRYRUN === 'false'` require
`STRIPE_SECRET_KEY` present and `sk_live_…`. (b) Runtime guard: when the gateway is
the mock outside dev/test, have the checkout action `fail(400)` with a "magazinul nu
acceptă încă plăți" message (or hide the checkout button) instead of redirecting.

## HIGH

### H-1. Postgres `jsonb` scrambles dimension order — production tie-break contradicts the documented contract and every test
**Where:** `modules/quiz/scoring.ts:279-299` (tie-break), `:263-270` (dimension
order); stored via `modules/quiz/schema.ts:22-25` (`scoring` is `jsonb`).
**What.** The tie-break contract (comments, STATE.md BS-2, `scoring.spec.ts`) is
"equal scores → earlier declaration order in `dimensions` wins". But `dimensions` is
a JS object persisted in `jsonb`, and jsonb re-sorts keys (length, then bytewise).
**Verified against the live dev DB:** authored `ST, MN, RU, VU, SA, PE, AN, FU, EP`
is stored as `AN, EP, FU, MN, PE, RU, SA, ST, VU`; the band quiz's
`noapte, zi, obiceiuri` is stored `zi, noapte, obiceiuri`, and existing
`quiz_results.profile.dimensions` rows confirm production scored in scrambled order.
**Why it matters.** Archetype ties resolve to the wrong archetype (an ST/MN tie
produces MN; a sparse submission produces "Antena", not "Străjerul"); the band result
page renders dimension bars out of narrative order. The unit tests pass only because
they never round-trip through jsonb — they validate behavior production doesn't have.
**Fix.** Make order explicit: change `dimensions` to an ordered array
(`[{ key, label }]`) or add an explicit tie-break priority list (`order:
ArchetypeId[]`). Add a through-the-DB test asserting tie-break and dimension order
after storage; correct the comment and STATE.md.

### H-2. Anyone can re-activate marketing email to an address that unsubscribed — no re-confirmation ever happens
**Where:** `modules/crm/service.ts:177-193` (`unsubscribeByToken` revokes consents
but never clears `confirmedAt`), `:110-114` (`already-confirmed` short-circuit),
`modules/nurture/service.ts:30-37` (`isMailable`).
**What.** `confirmedAt` is a one-way, forever flag that survives unsubscribe, and the
capture/newsletter actions grant `newsletter: true` for whatever email the visitor
typed. Chain: victim once confirmed, later unsubscribed → attacker submits the
victim's email on a quiz result (or footer form) → consent re-granted, no confirm
email sent (`already-confirmed`), `isMailable` true → victim is enrolled in
`protocol-arhetip-somn` and mail resumes after an explicit withdrawal.
**Why it matters.** This is exactly what double opt-in exists to prevent; it is
scriptable harassment (the 10/IP/hour throttle only slows it), and the stored
"consent" is one the data subject never gave — a GDPR problem in itself.
**Fix.** Treat confirmation as per-grant, not per-address-forever: clear
`confirmedAt` on unsubscribe, or require a fresh confirm whenever `newsletter`
transitions to granted after a prior revocation (e.g. `consents.newsletter.at >
confirmedAt` ⇒ not mailable, send confirm). The `already-confirmed` fast path should
apply only while the original grant was never revoked.

### H-3. One IP can burn the entire global email budget — refused per-IP requests still drain the global counter
**Where:** `src/lib/server/rate-limit/public-email.ts:41-45`.
**What.** The per-IP and global counters are consumed unconditionally in
`Promise.all`, and `consumeRateLimit` counts refused requests too (`core.ts:64-70`).
So requests from an IP already over its 10/hour cap keep incrementing the shared
`:global` counter (200/hour) at full request rate.
**Why it matters.** The global cap was added as the anti-mailbomb availability
control; as written, the cheap single-IP attack *is* the global-starvation attack —
every legitimate visitor gets 429 on quiz capture and footer newsletter for the rest
of the window.
**Fix.** Consume the per-IP counter first and short-circuit: only consume a global
slot if the IP check passed. (Sequential, not `Promise.all`.) Add a test that an
over-cap IP does not drain the global bucket.

### H-4. Rate limiting keys on unconfigured `getClientAddress()` — behind a proxy, either everyone shares one bucket or the throttle is spoofable
**Where:** capture `+page.server.ts:39`, `routes/(public)/newsletter/+page.server.ts:23`;
prior audit `docs/AUDIT-2026-07-09.md:136-138` (M2, still open).
PLAUSIBLE on deployment config; verified that no adapter address configuration exists
(no `svelte.config.js` for the web app; `vite.config.ts` sets no `csrf`/address opts).
**What.** On adapter-node behind any reverse proxy with default settings, either all
clients collapse to the proxy's socket IP (the per-IP cap of 10 becomes a site-wide
cap of 10) or a naive header-trust fix lets attackers forge `X-Forwarded-For` for a
fresh bucket per request.
**Fix.** Configure the trusted proxy hop depth explicitly per target (adapter-node
`ADDRESS_HEADER`/`XFF_DEPTH`; Vercel's forwarded header is trustworthy) and document
it in DEPLOYMENT.md. Until then, the per-IP throttle is not load-bearing.

### H-5. No security headers at all — no CSP, no frame-ancestors, no nosniff, no HSTS, no Referrer-Policy
**Where:** `apps/web/src/hooks.server.ts:20-78`; `vercel.json` (crons only);
DEPLOYMENT.md proxy section never mentions headers.
**What.** The hook chain sets zero security headers and there is no Kit `csp` config.
`/admin/login` is frameable by any attacker page (clickjacking a staff login), and
the site renders `{@html}` in five public routes where `sanitize-html` is the *only*
defense — one sanitizer bypass becomes full stored XSS with no CSP backstop. Nothing
ever emits HSTS on the adapter-node target.
**Fix.** Add a small `handleHeaders` to the `sequence()`: `X-Content-Type-Options:
nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options:
DENY` / CSP `frame-ancestors 'none'`, HSTS when `PUBLIC_SITE_URL` is https, and a
report-only `default-src 'self'` CSP as a starting point. One hook covers both
deploy targets.

### H-6. The public quiz-submit endpoint is completely unthrottled, and `quiz_results` has no retention sweep
**Where:** `routes/(public)/quiz/[slug]/submit/+server.ts:15-42`;
`src/lib/server/retention.ts:42-51` (sweep covers chat/rate-limits/ledger/nurture,
never `quiz_results`). Found independently by two review passes.
**What.** Every other public write is throttled (email capture, newsletter, chat,
admin login); the landing page's primary CTA endpoint is not. Each POST inserts a
`quiz_results` row with up to ~256 KB of attacker-chosen `answers` jsonb; the
idempotency token is optional and client-supplied, so it provides no protection.
**Why it matters.** A dumb loop grows the table unbounded at wire speed (billable
per-request on Vercel+Neon), inflates admin `resultsCount`, and poisons the
"anonymous statistics" the erasure policy leans on. There is no cleanup path, ever.
**Fix.** Consume a `quiz-submit` scope through the existing `rate_limits` core
(per-IP + global) before `submitQuiz`; shrink the body cap (a legitimate 12-answer
payload is ~2-3 KB, not 256 KB); consider a retention sweep for unclaimed results.

### H-7. `launch:check` lets a live deploy ship with the mock chat provider and the fake-AWB mock courier
**Where:** `src/lib/server/launch-check.ts:59-61,108-114`;
`modules/chat/select.ts` (mock default); `modules/shop/courier.ts:68` (mock default);
`config/sites/sleep.ts:41` (`chatWidget: true`).
**What.** The preflight already uses `EMAIL_DRYRUN=false` as its "this env is live"
signal to reject `sk_test_` Stripe keys, but in that same live env it says nothing
about `CHAT_PROVIDER` unset/mock or `COURIER_PROVIDER` at all. Consequences of a
preflight-green deploy: the site-wide chat widget serves three keyword-matched canned
answers as the "assistant", and real paid orders get deterministic fake AWBs and fake
tracking URLs mailed to customers (DEPLOYMENT.md itself warns the mock is "never for
a customer parcel"). Only human checkboxes in LAUNCH-CHECKLIST.md guard this.
**Fix.** In the production branch of `launchCheckProblems`, flag
`CHAT_PROVIDER !== 'anthropic'` and `COURIER_PROVIDER !== 'sameday'` as problems
(mirroring the sk_test_ rule); additionally block the AWB action at runtime when the
courier is the mock outside dev. Together with C-1's key check, one rule family keyed
on the existing live signal closes the whole mock-in-prod class.

### H-8. Admin product save in a keyless env writes `prod_mock_N` Stripe ids into the DB and permanently breaks re-sync when real keys arrive
**Where:** `routes/admin/(shell)/products/[id]/+page.server.ts:69-76`,
`modules/shop/sync.ts:28-33,56-60`, `modules/shop/stripe-gateway.ts:43-48`.
**What.** Every admin save runs `syncProductToStripe`; keyless, the mock persists
`prod_mock_N`/`price_mock_N` into the product row. Later, with real keys, the sync
sees `stripeProductId` set and calls `stripe.products.update('prod_mock_1', …)` →
`No such product` → `{ ok: false, error: 'gateway' }` forever. The documented launch
plan ("keys arrive → admin re-sync", STATE.md BS-6) is exactly the sequence that
hits this; any pre-launch typo fix arms it. `getPrice` handles missing resources;
`updateProduct` does not — the asymmetry is the bug.
**Fix.** Skip persisting mock ids entirely when the gateway is the mock, and/or in
`syncProductToStripe` treat `resource_missing` on update as "create fresh" (which
also heals a Stripe account switch).

### H-9. The 3 fictional demo products are live in the production catalogue, and re-seeding reverts an admin's attempt to retire them
**Where:** `src/lib/db/seed.ts:149-191` (products; `onConflictDoUpdate` set includes
`status: 'active'` at `:178,185`), `:52-83, 204` (demo articles force-republished),
`:97-122` (seed quizzes likewise fully overwritten incl. `status`).
**What.** The demo mask/tea/lamp (89,90 / 34,50 / 129,00 lei) are seeded `active` and
pillar-tagged, so they are purchasable in `/magazin` between the 33 real SKUs. If an
operator archives them in admin, the next `db:seed` silently reactivates them; the
same clobber pattern force-republishes demo articles and overwrites any admin edit to
the two seeded quizzes. `launch-check` has no rule about `seed-product-*` /
`seed-article-*` ids (unlike its placeholder-settings gate).
**Why it matters.** The moment C-1 is fixed, a customer can pay real money for a
product that does not exist (refund + storno invoice + courier cancellation). STATE.md
lists "a decision on retiring the demo products" as open — it is not optional.
**Fix.** Gate demo seeding behind a dev/e2e flag (or seed `draft` outside dev), drop
`status` from every seed conflict-update set so admin state wins, and add a
launch-check assertion that no `seed-*` ids are active/published.

### H-10. VAT: the single 21% default rate is likely wrong for food supplements (PLAUSIBLE — confirm with the accountant)
**Where:** `modules/settings/registry.ts:170-180` (`invoice.vatRateBp` default 2100),
`modules/invoice/service.ts:162-177`.
**What.** All 33 catalogue products are food supplements, which in Romania fall under
the reduced rate (11% after the Aug 2025 reform), not the 21% standard rate the
single site-wide setting defaults to. Verified in code: there is exactly one global
rate, nothing in the settings UI, launch-check, or docs hints a supplements shop
should change it, and shipping silently inherits the goods rate.
**Why it matters.** Prices are gross, so customers pay the same — but every invoice
and e-Factura XML would overstate VAT (~37,49 lei declared vs ~21,41 owed on a
216-lei order) and understate net revenue: a systematically wrong fiscal record from
day one that looks fine on every screen.
**Fix.** Confirm the classification before launch and set the value accordingly; add
a hint on the setting + a launch-checklist line; consider per-product `vatRateBp` for
the day two rates coexist.

## MEDIUM

### M-1. The result `?/email` action skips the guards the page load enforces — slug-mismatch claims, an existence oracle, and cross-claim mis-targeting
**Where:** `routes/(public)/quiz/[slug]/rezultat/[resultId]/+page.server.ts:22-59`;
`modules/quiz/funnel.ts:81-84`; `modules/nurture/service.ts:142-168`.
**What.** (a) The action never verifies `found.quiz.slug === params.slug`, quiz
`published` status, or the site-pillar gate the load and submit endpoint enforce — a
result of quiz A (or of an unpublished quiz) can be claimed through quiz B's URL by
direct POST. (b) 404-vs-success response shapes make the action an existence oracle
over result IDs (UUIDs, so enumeration is expensive — hence medium). (c)
`claimQuizResult` unconditionally overwrites `quizResults.subscriberId`, and
`enrollFromQuizResult` re-reads the row's owner rather than the claimer, so an
attacker holding a shared result URL can attach their subscriber to a victim's result
and receive the victim's profile by email; racing claims can enroll the wrong
subscriber. (d) `{{resultUrl}}` resolves to the subscriber's *latest* result for the
slug, which after a retake may not be the result that triggered the enrollment.
**Fix.** Run the load's slug/status/pillar checks at the top of the action; return
the generic `{ sent: true }` shape for not-found; keep the first `subscriberId` once
set unless re-claimed by the same subscriber; pass the claimed `subscriberId` into
`enrollFromQuizResult` explicitly and store the originating result id on the
enrollment for `{{resultUrl}}` resolution. Add tests for the cross-slug and
cross-result cases (none exist).

### M-2. Crafted quiz submissions break every scoring invariant server-side
**Where:** `modules/quiz/scoring.ts:135-141,156-168`;
`modules/quiz/service.ts:213-235` (`sanitizeSubmittedAnswers`).
**What.** Sanitization only filters unknown `questionId`s — it never validates value
shape against the question type. Verified consequences of a hand-crafted POST:
a single-select answered with `["ru","ru","ru",…]` is scored as a multi-select with
duplicates summed (any archetype forceable, `score` can exceed `maxScore`); an empty
`answers: []` bypasses `required` and still yields a stored winner; duplicate
`questionId` entries survive into stored `answers` (contradictory admin rows).
Integrity/abuse only (it corrupts the submitter's own row), but junk rows are
indistinguishable from real funnel data.
**Fix.** In `sanitizeSubmittedAnswers` (it already walks the schema): enforce
per-type value shape, restrict to declared option values, dedupe multi-select values
and `questionId`s, and reject (or flag) submissions missing required questions. Add
hostile-payload tests — this path is entirely uncovered.

### M-3. Quantity is never checked against stock — a single order of 26 units with stock 25 is charged, then flagged oversold
**Where:** `modules/shop/checkout.ts:167-172`, `modules/shop/service.ts:44-46`,
`modules/shop/cart.ts:22-25` (`CART_MAX_QTY` 99, no stock clamp).
**What.** Availability is only `stock <= 0`; quantity is clamped to 99, never to
`product.stock`. Any cart line of 26–99 units passes pre-payment checks, Stripe
charges the full amount, and the webhook clamps stock to 0 and flags `oversold` — a
mechanism designed for the rare two-buyer race now fires on the common single-buyer
bulk order (multi-unit supplement orders are normal; stock 25 is low enough to hit).
**Fix.** In `loadCartDetails` and the product-page `add` action, mark the line
unavailable (or clamp with a message) when `qty > product.stock`. Keep the webhook
clamp as the race backstop. No test covers qty-over-stock today.

### M-4. No `pending → paid` path: a delayed-payment order is stranded forever — and still gets a confirmation email
**Where:** `modules/shop/webhook.ts:199,288,309-324,416-423`;
`modules/shop/stripe-gateway.ts:74-111` (no `payment_method_types` pinned).
**What.** `checkout.session.completed` with `payment_status !== 'paid'` creates a
`pending` order and nothing can ever flip it: no
`async_payment_succeeded/failed` handlers, no admin "mark paid", no other write of
`status: 'paid'` (grep-verified). A pending order gets no invoice, is invisible in
the admin work queue, has its stock already decremented (never restored on failure) —
and the confirmation email is sent anyway. Because the session doesn't pin
`payment_method_types`, enabling any delayed-notification method in the Stripe
dashboard silently arms this with zero code change.
**Fix.** Cheapest: pin `payment_method_types: ['card']` and document it. Correct:
handle the two async events (paid → invoice; failed → restock) — the idempotent
ledger infrastructure already exists. No webhook fixture exercises async payment.

### M-5. Night-map chips are compile-time constants — an admin slug rename or deactivation 404s the landing page's product links with nothing failing
**Where:** `routes/(public)/+page.server.ts:14-15`, `modules/shop/night-map.ts:38-58`,
`night-map.spec.ts:39-56` (pins committed bundles only).
**What.** The landing load returns `NIGHT_MAP_SKUS` verbatim with no DB check; the
spec pins against committed bundles, but `updateProduct` lets admins rename slugs or
archive products, and the DB then drifts from the bundles with no test, no build
error, and a hard 404 from the site's highest-traffic surface. Zero-stock is handled
gracefully; rename/deactivate is not.
**Fix.** One cheap query in the landing load (`slug IN (…) AND status='active'`) and
filter the chips — segments degrade gracefully with fewer chips. Optionally assert
the 11 SKUs active in `sleep-content.spec.ts`, which already runs against a seeded DB.

### M-6. Product pages ship with no Product JSON-LD, one shared meta description for all 36, and no image anywhere; articles have no og:image and no site-wide fallback exists
**Where:** `routes/(public)/magazin/[slug]/+page.svelte:11-16` vs the fully-featured
`components/Seo.svelte`; all 73 bundles `coverMediaId: null`; `Seo.svelte:41` emits
no og:image and downgrades to `twitter:card summary` when `ogImage` is null.
**What.** Blog articles use Article JSON-LD + social cards; product pages pass
nothing: no `Product`/`Offer` schema (no price/availability in search results),
`description={m.shop_tagline()}` identical across all SKUs, no image. `/blog` is a
uniform grid of 43 blank colored boxes; no article or product has an og:image, and
there is no site-default fallback. STATE.md's launch list names product images but
never article covers or the og fallback — the gap is untracked.
**Why it matters.** These 33 pages are the site's only commercial long-tail SEO
surface, competing against zenyth.ro's own pages for identical product names;
shipping them as imageless near-duplicates wastes the launch's main organic channel.
**Fix.** Add Product JSON-LD (name, `offers.price` via `centsToDecimal`,
`priceCurrency: 'RON'`, availability; valid without an image); derive per-product
meta descriptions from the first sentences of `descriptionMd` (excluding the
Sursă-preț line); add a static branded fallback og:image in `Seo.svelte`/site
config; track article covers as a launch item alongside product images.

### M-7. Content import is keyed purely on slug — a slug rename orphans a live published row in every already-seeded database
**Where:** `modules/content/import.ts:186` (articles), `:251` (products);
stale-deletion loop in `scripts/articles-from-initialdata.ts` (~line 148).
**What.** If a slug is edited in `topics.json` (or a zenyth URL changes),
regeneration deletes the stale bundle *file*, but the next seed on an existing DB
creates a second article under the new slug while the old row stays published — both
in `/blog`, both in `sitemap.xml`, duplicate content, and a stale URL that never
404s. The idempotence specs can't catch it because they only ever test fresh DBs.
**Fix.** Carry a stable external key in the bundle (e.g. `topic.id` as an
`importKey` column) and upsert on that; or ship a `content:prune` step that
unpublishes rows whose slug is absent from committed bundles.

### M-8. "Re-import is a no-op" is false for `updated_at` — sitemap lastmod and JSON-LD dateModified churn on every deploy
**Where:** `modules/content/import.ts:194,262`; consumed by
`routes/sitemap.xml/+server.ts` and article JSON-LD.
**What.** The update path unconditionally sets `updatedAt: new Date()` even when
nothing changed — verified live in the dev DB (unchanged article stamped by a
re-seed). Every prod re-seed marks all 73 items "modified today"; crawlers learn to
ignore lastmod and real edits lose their signal. Row-count-only idempotence tests
pass regardless.
**Fix.** Compare mapped fields against the existing row and skip the UPDATE (or the
`updatedAt` bump) when equal; pin with a spec asserting `updated_at` stability
across re-import.

### M-9. The conversion scripts' stale-deletion sweep can silently delete hand-authored bundles
**Where:** `scripts/articles-from-initialdata.ts` and
`products-from-initialdata.ts` (delete any `/^\d{4}-.+\.json$/` of their type not
regenerated); `content/README.md` documents an author-in-admin-and-export workflow
into prefix-numbered files.
**What.** Nothing marks `content/sleep/` as script-owned; a maintainer exporting
`0405-articol-nou.json` per the visible convention loses it on the next
`articles:from-initialdata` run (one log line; if uncommitted, gone). Related
robustness: one malformed JSON aborts the sweep mid-deletion, and outputs are plain
`writeFile` (no tmp+rename), so an interrupt leaves a half-old/half-new dir.
**Fix.** Restrict deletion to the generated ranges (0010–0400 / 1010–1330) or a
generated-files manifest; document ownership in `content/README.md`; try/catch the
sweep's parse; write via temp+rename.

### M-10. GDPR: erasure is excellent, but there is no subject-access/portability export at all
**Where:** `modules/gdpr/` (only `erase.ts` + consent/cookies); `scripts/` has only

request gets answered with hand-written SQL under a statutory deadline.
**Fix.** A `pnpm subscriber:export -- --email …` CLI querying exactly the tables
`erase.ts` already touches, printing JSON. Small and symmetric with the delete tool.
